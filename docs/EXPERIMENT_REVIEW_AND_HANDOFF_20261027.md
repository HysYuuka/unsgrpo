# 无人工高光标注实验审查与执行交接

本文供执行 agent 接手 Qwen SFT 与 GRPO 视频高光实验使用。目标是在当前单张 RTX 4090 上完成一轮可复核、预算固定的研究验证，回答代理信号、学生学习和 GRPO 续训各自是否带来收益。

原方案：[无监督高光检测 Qwen SFT GRPO 实验方案与数学推导](/root/无监督高光检测_Qwen_SFT_GRPO_实验方案与数学推导_20261027.md)。本交接补充执行次序与验收条件；原方案中的超参数仍是首轮候选，需通过技术检查后冻结。

## 综合判断

值得开展首轮实验。方案的优点是任务边界明确，训练标签与评价标签隔离，设置直接代理和继续 SFT 对照，并认真处理 SFT 参考策略、窗口对齐、计算预算与统计单位。平均余弦化简、组均值 baseline 的比例因子、KL 估计条件、理想 KL 正则最优分布等推导在文中假设下成立。它们支持对象定义和局部数值检查，实际高光效果仍由独立实验决定。

优先解决以下研究问题。

1. **代理测量的是什么。** 当前重复性分数严格等于片段特征与簇均值的点积，实际测量 CLIP 特征空间中的类内典型性。常见背景可能得高分。四帧特征取均值对帧顺序置换不敏感，监督本身无法区分动作先后；Qwen 的时序能力能否补偿，要由实验确认。原视听方法已报告学习模型超过直接伪分数的实验，但其特征、模态和模型不同，不能直接迁移数值预期。[原论文第 4.3 节](https://arxiv.org/html/2407.13933v2)

2. **全视频目标是否能从局部输入预测。** 由于平均秩之和为 T(T+1)/2，q=(midrank−1/2)/T 满足每个视频的平均 q 恒为 0.5。它表示视频内相对位置，不能解释为跨视频高光概率。16 格概览加局部窗口也未必包含确定完整视频百分位所需的信息；即使实现正确，平方误差仍可能受到 E[Var(q|X)] 的限制。

3. **训练库包含自身的影响。** R0 在训练时包含当前视频，测试时只参照训练库。视频较长或簇很小时，自视频重复可能主导分数；单视频簇没有跨视频参照。报告簇大小、自视频片段占比和 singleton 数量。整视频排除可作为分数诊断，首轮不因此新增训练分支。

4. **奖励改善的来源。** 全视频百分位能放大很小的原始差异，整数 SFT 标签又会产生并列。排序奖励上涨可能来自去并列、格式修复或伪监督拟合，而非人类高光能力改善。必须拆开合法率、排序奖励、校准奖励和真实评价。

5. **收益归因的范围。** S+ 使用 token 交叉熵，G-RANK 使用排序与校准奖励，两者同时改变了目标和训练方式。首轮六组能检验这套训练配方，尚不足以证明强化学习必不可少。若结果有希望，第二阶段再补同伪标签的直接回归或排序学习对照，尽量匹配模型、输入和预算并披露剩余差异。

### 阶段一 资产与评价定义

1. 核对代码、数据来源、视频身份、完整时长、模型版本与许可。只下载本轮需要的资产。缺失或损坏视频形成明确清单，所有方法使用同一集合。
2. 按 source_group 划分，再生成窗口。固定 split、数据哈希与随机种子；训练聚类和参照库只用训练视频。训练提示排除人工类别、标题、GT 与伪答案。
3. 在正式训练前确定评价输入、时间轴、标注者维度、二值化规则、并列处理和平均顺序。TVSum 官方是视频摘要重要性标注数据，不能仅凭数据集名称把某个自定义 AP 称为高光 top-5 mAP。[TVSum 官方说明](https://github.com/yalesong/tvsum)
4. V0 作为原方案定义的内部诊断；V1 必须绑定可核验的来源协议、代码版本及数值检查。用手算小例子验证指标和区间映射，能获得公开参考输出时再做交叉验证。V1 暂不能完成时可以继续工程验证或明确标记的 V0 试验，不能进行跨论文数值比较。
5. 若要根据人工标注提前选择奖励、prompt 或方法，必须另划开发集，并披露使用了标签进行方法选择。保留最终测试来源，不能把已用于改方法的集合继续称作未见测试集。

验收产物：资产清单、split manifest、评价协议说明、指标测试结果、缺失项及处理决定。

### 阶段二 环境与真实数据链路

加载 `/root/autodl-tmp/unsgrpo/storage-env.sh`。在仓库外创建独立研究环境，按实际兼容性核验 ms-swift 4.6.0、Transformers、PEFT、TRL、PyTorch、qwen-vl-utils 等依赖，保存完整版本与模型 resolved revision、权重哈希、processor 和 chat template。版本号固定不等于兼容性已经通过。

先运行本机 CPU 测试，再用真实训练视频检验 PTS 解码、末段、短视频、抽帧误差、CLIP 特征及 UMAP 路径。PCA 调试结果单独标记。至少查看 processor 实际缩放后的输入，检查小动作、时间文字和概览格是否可辨。

全量预检实际编码长度、媒体 placeholder、image/video grid、处理前后帧数和片段 ID；超长、删样本、重采样错位或截断必须显式失败并修复。GRPO 在 v4.6.0 源码中默认采用左截断，`strict=true` 不能替代这项检查。[参数处理源码](https://raw.githubusercontent.com/modelscope/ms-swift/v4.6.0/swift/arguments/rlhf_args.py)

在训练域输出代理诊断：簇规模、自视频占比、raw 分布与跨度、q 分布、整数目标并列率、窗口排序权重和 W、代表性高低分片段。可计算 R0 与整视频排除分数的差异用于定位自参照问题。依据诊断改变主方法必须发生在协议冻结前，并保留版本记录。

验收产物：依赖锁、真实视频预处理记录、输入审计、训练域代理诊断、数据文件哈希。

### 阶段三 单卡完整训练闭环

先用训练视频做技术检查；GRPO 从 `PROMPTS=1,G=4,steps=4` 起跑。必须覆盖生成、奖励、old/ref/current log probability、反向传播、optimizer update、保存和重载推理。随后再检查正式并发配置。训练 microbatch=1 不能证明 rollout 阶段显存足够；默认正式配置每次生成批含 16 条 completion。[ms-swift 参数定义](https://swift.readthedocs.io/en/v4.6/Instruction/Command-line-parameters.html)

必须逐项提供证据：

- 同组 completion 绑定相同 request_id、媒体张量、片段顺序和 q；奖励元数据长度正确还不够，内容对应关系也要正确。
- SFT 只监督 assistant 答案；GRPO 的 messages 没有 assistant 伪答案、q 或 GT。
- JSON 解析严格；合法与非法回答有可验证差异；全部输出同分、全部奖励相同、截断回答均有明确处理。
- 新 LoRA 有有限梯度，更新后参数确实改变；保存可训练参数名称，确认视觉塔、对齐器和底座被冻结。
- 合并 S0 前后比较固定答案的 token log probability；三条后续分支从同一合并底座新建相同规格 LoRA。
- 禁用新 adapter 得到固定 S0 参考，更新后参考仍不变；old/ref/reward/advantage 停止梯度，当前 log probability 保留梯度。
- prompt 和 padding 不进入 completion loss；EOS、长度归一化、标准差修正及采样分布设置有实测记录。
- 记录生成、概率计算、反向各阶段峰值显存与耗时，验证保存重载；若声称精确断点续训，还需验证优化器、scheduler、随机状态及数据游标恢复。

OOM 先检查 rollout 并发和调度。若必须修改输入数、帧数、分辨率或有效 batch，登记新方案，并同步调整比较组和曝光预算。技术检查通过不代表正式训练已经完成。

### 阶段四 冻结并执行首轮矩阵

保留 B0 直接代理、B1 Qwen 零样本、S0 共同 SFT 端点、S+ 继续 SFT、G-CAL、G-RANK。主比较为 G-RANK 减 S+；B0 和 B1 用于判断代理与预训练先验的作用。

以原方案为起点：S0 为 256 次成功更新、每次 16 个输入曝光；后续三个分支各 256 次成功更新、每次 4 个输入曝光，两个 GRPO 分支每输入生成 4 条回答。S0 共 4096 次曝光；每个后续分支共 1024 次曝光，每个 GRPO 分支共 4096 条 rollout。只有真实采样器账本与这些数值一致时才能如此报告。

锁定 split、窗口池、prompt、伪标签、视觉输入预算、LoRA、奖励、优化器与推理配置。记录实际 request_id 顺序、重复次数、唯一窗口数、有效 token、成功更新、GPU 小时和峰值显存。曝光次数不是独立样本数，相同曝光也不是相同计算。

第一轮使用一个 seed，结论作为可行性证据。固定终点为主结果；不按测试指标挑 checkpoint、换 split、选择性延长某分支。若 GPU 或数据故障导致中断，恢复原配置或为受影响的比较整体重新登记。

### 阶段五 推理与结果解释

所有训练端点使用相同全覆盖窗口、greedy 解码、视觉预算、输出长度和失败处理。按原方案将非法窗口计入主指标，同时报告其比例。推理结果每个 run 使用独立新文件，并校验 request_id 唯一、无缺失、无额外行；ms-swift 对已存在的 result_path 会追加结果。[推理结果参数](https://swift.readthedocs.io/en/v4.6/Instruction/Command-line-parameters.html)

冻结预测文件及其哈希后读取评价标签。采用真实时间区间重叠映射，保证完整覆盖。主结果按视频或独立来源组做配对分析；窗口不能充当独立样本。单 seed 的视频 bootstrap 不包含训练随机性。

一起交付四类结果：代理奖励、格式与稳定性、人类高光评价、训练及推理成本。补充合法回答上的奖励分解、跨窗口分差、常数输出率、组奖励方差和定性失败案例，解释收益是否主要来自格式修复或去并列；条件化诊断不能替代全样本主指标。

按证据决定下一步：

- B0 强而学生弱：优先查输入、目标可预测性、训练有效性与尺度绑定。
- S0 超过 B0，GRPO 与 S+ 接近：学习有用，GRPO 的额外价值尚未成立。
- 代理奖励上升而人类指标下降：报告代理错位候选，定位背景、伪类别或局部信息缺失。
- G-RANK 稳定优于 S+：再规划三个完整训练 seed、独立来源和直接排序学习对照。每个 seed 包含自己的 S0。
- 质量提高但成本显著增加：报告质量与成本取舍，再决定轻量学生方案。

首轮完成后提交结果与下一阶段建议；扩展研究以结果为依据。

## 最终交付与故障处理

交付一份首轮结果报告，附完整运行命令、配置及数据哈希、模型版本、共同 S0 身份、各分支端点、依赖锁、逐视频指标、统计结果、曝光账本、成本、磁盘使用、失败清单和 Git 同步状态。所有 PLANNED、RUNNING、COMPLETED、FAILED 状态都应能追溯到日志。

数据来源交叉、标签进入训练提示、ID 错位、参考策略漂移、输入截断、非有限梯度、预测覆盖缺失属于必须修复的实现故障。CPU 测试通过和 loss 下降都不能覆盖这些故障。结果不理想本身也是有效研究输出，应按预登记方案完成比较并报告，不通过测试集搜索或无限增加训练掩盖。

评价这轮工作的标准是：能否可信地回答代理是否有效、学生是否受益、GRPO 是否值得其额外成本，并给出可复核证据。
